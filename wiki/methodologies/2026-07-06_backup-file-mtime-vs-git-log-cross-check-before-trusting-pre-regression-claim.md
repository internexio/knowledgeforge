# Backup files timestamped near a "fix" commit are not automatically "pre-regression working reference"

## The trap

When a bead, incident report, or hand-off note cites a timestamped backup file (e.g., `~/.claude/agents/*.md.bak-20260629-1000`) as the "pre-regression, working" shape, the natural inference is: the operator preserved a working snapshot before something broke it. **This inference is often wrong.**

Common pattern: an outage is diagnosed, backups are made as part of the investigation, then a fix is applied. The backup timestamp falls INSIDE the broken window, not before it. Cross-check the backup's mtime against the git log for the fix that supposedly introduced the regression before trusting.

## Concrete grounding — knowledgeforge-core-oxp (2026-07-06)

The bead's description read:
> "Working reference (pre-regression, backups at ~/.claude/agents/*.md.bak-20260629-1000)"
>
> `<!-- Generated by kf-compile -->` on line 1
> then `---name: critic ... ---`
> then body

I initially planned to fix the compiler to reproduce that shape. Before writing code, I cross-checked:

```
$ stat -f "%Sm" ~/.claude/agents/critic.md.bak-20260629-1000
Jun 29 10:00:10 2026
$ git log --format="%h %ai %s" 5981a7e -1
5981a7e 2026-06-29 10:18:28 -0700 fix(compiler): skip leading comment for frontmatter-first agent files
```

The "pre-regression working" backup was captured 18 minutes BEFORE commit 5981a7e was applied. Commit 5981a7e's message describes: "kf-compile unconditionally prepended `<!-- Generated -->` before all output content. When content begins with YAML frontmatter (---), this displaced --- to line 2, causing the Claude Code agent loader to silently skip the file. All 11 KF agents broke; [project] was dark for 3 nights (2026-06-27/28/29)."

So the backup at 10:00 was NOT a pristine working state — it was a snapshot captured during the tail end of a 3-night outage, 18 minutes before the fix that unblocked agent discovery. Trusting the backup shape would have re-introduced the 3-night outage. The correct pre-regression shape (agents WITHOUT leading comment, `---` on line 1) can be verified against still-working non-KF agents (`~/.claude/agents/cos-*.md`).

## The verification move

Before treating a backup file's shape as "known good":

1. `stat -f "%Sm" <backup-file>` — get the backup mtime
2. `git log --after="<mtime - 1h>" --before="<mtime + 24h>" --oneline -- <affected-code-path>` — was a fix committed in the surrounding window?
3. Read the fix commit's message. If the message describes the SAME problem class as the backup's shape represents, the backup is probably a snapshot of the broken state, not a pristine reference.
4. Corroborate against still-working sibling artifacts (in this case, non-KF agents that weren't affected).

## When this applies

Any hand-off, bead, or incident report that cites a specific backup file as "working" or "pre-regression" state. Even when the operator authored the bead themselves, memory can invert timelines (the operator here believed the backup pre-dated the fix).

## When this does NOT apply

- Long-lived backup files (mtime months or years before the incident) — those are almost certainly pre-regression.
- Backups produced by CI or automated snapshotting on a known cadence — cadence gives ground-truth.
- When the working reference is a git tag or release branch — that's canonical, not a wall-clock inference.
