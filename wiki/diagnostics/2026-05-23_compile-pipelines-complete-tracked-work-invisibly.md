# Compile Pipelines Complete Tracked Work Invisibly

## The Pattern

In multi-repo architectures where a source-of-truth repo (Repo A) feeds a compile pipeline that produces a derived repo (Repo B), issues tracked in Repo B may be marked as "to-do" but are actually already completed by the pipeline. The deliverable lands in Repo B automatically; the issue tracker never gets closed.

This creates a systematic drift problem: strategists reading the issue backlog see work-to-do; reality is 5 minutes of file inspection away from "already done, close it."

## When to Suspect This

You have:
- A multi-repo setup (source A → derived B via compile/codegen)
- An open issue in the derived repo (B)
- The issue's deliverable looks like the kind of thing the pipeline *would* produce
- No manual edits to the deliverable (the pipeline runs unattended)

## Diagnostic Procedure

**Step 1: Check the deliverable's actual state in Repo B**

- Does the file exist at the path the issue specifies?
- When was it last modified? (Check `mtime` or git log)
- How large is it? How many lines?

**Step 2: Look for compile metadata**

Compiled files often carry headers indicating their origin:
```
<!-- Generated by kf-compile | source: NN_*.md | compiled: 2026-05-20T00:07:32Z -->
```

or

```
# AUTO-GENERATED FROM: source-file.md
# Compile run: 2026-05-20 17:13:00 UTC
```

If present, the file was definitely produced by the pipeline, not manual work.

**Step 3: Compare against the issue's baseline**

When the issue was filed, someone captured the deliverable state (or the absence of it). Compare:
- Baseline file size: was it 0 KB (missing)? 5 KB (rough draft)?
- Current file size: is it substantially larger/different?
- Baseline: did the acceptance criteria describe what the file *should* look like?
- Current: does the file now match that description, despite no manual edits in the current session?

**Step 4: Verify by reading**

Don't assume. Read the current deliverable and ask: does this match what the issue asked for?

If yes → the pipeline did the work.
If no → the issue is still genuinely open.

## Real Examples from KF Phase 1 Validation (2026-05-22)

### Example 1: kf-f1j — Condense load-bearing module docs

**Baseline (2026-05-18):** Module docs in knowledgeforge-cc were 9.8 KB–40.8 KB each (~2.5K–10K tokens).

**Expected deliverable:** Condensed versions ~5-10x smaller, with specs retained in source repo.

**Status on 2026-05-22:**
- Files existed at expected paths: `docs/knowledgeforge/NN_*.md`
- All carried `<!-- Generated by kf-compile | source: NN_*.md | compiled: 2026-05-20T00:07:32Z -->` headers
- Sizes: 2.4 KB–3.4 KB each (~600–850 tokens)
- Pipeline had run on 2026-05-19 17:13
- **Conclusion:** Already done by the pipeline. Issue should be closed.

### Example 2: kf-8z4 — Build 30-prompt routing test suite

**Baseline (2026-05-18):** No test suite existed in knowledgeforge-core/tests/.

**Expected deliverable:** 30 routing test cases covering classifier decision paths.

**Status on 2026-05-22:**
- Suite existed at knowledgeforge-core/tests/routing_tests.py
- 31 test cases (exceeded spec by 1)
- 239-line test runner (run_routing_tests.py)
- Tests verified all major routes; coverage matched acceptance criteria
- **Conclusion:** Already done by the pipeline. Issue should be closed.

## When This Pattern Does NOT Apply

**Do not use this diagnostic if:**

1. **No compile pipeline exists** — work is purely manual, no auto-completion possible.

2. **The pipeline doesn't own the deliverable's path** — if it's a manually-curated file (configs, settings, decisions), the pipeline doesn't generate it. Example: `settings.json` manual entry for UserPromptSubmit hook. The hook script exists, but settings.json wasn't touched by any pipeline.

3. **The deliverable is behavior, not a file** — pipelines produce artifacts (files, configs, schemas), not runtime behavior. An issue like "fix race condition" can't be auto-completed by a codegen pipeline, even if related code changed.

4. **The issue explicitly requires manual judgment** — "decide which option to pick", "evaluate trade-offs", "approve design". Pipelines can't make decisions.

## Root Cause

In multi-repo setups, the issue tracker and the build artifact exist in separate systems:
- Issue tracker: lives in Repo B (derived)
- Build artifact: produced by pipeline from Repo A (source)

There's no integration point between them. When the pipeline succeeds, the artifact updates automatically. The issue remains open because nobody wired a completion hook.

The fix is architectural: either (a) track such work in Repo A (the source of truth), OR (b) add a compile-completion hook that scans Repo B for issues that match completed artifacts and auto-closes them.

KnowledgeForge currently has the (a)-style problem: issues live in knowledgeforge-cc (derived), but the source work happens in knowledgeforge-core (source). When the compile pipeline runs, knowledgeforge-cc's issues don't know about it.

## Operational Impact

**For strategists & planners:** When surveying backlog, spot-check open issues against actual file state. A 5-minute file inspection can surface "already done" work and free up the issue for closure.

**For build pipeline owners:** If your pipeline produces tracked deliverables (specs, configs, test suites), add a post-compile audit step that checks for related open issues and surfaces them for human closure (don't auto-close; provide a report).

## Counter-Example: When File Existence ≠ Done

**Issue kf-x45:** Register UserPromptSubmit hook in settings.json.

- ✓ Hook script exists: `.claude/hooks/kf-route.py` (produced by pipeline)
- ✗ Config entry missing: settings.json has no UserPromptSubmit entry

The pipeline produced the hook, but the configuration (which lives in a manually-maintained settings file) was not touched. The issue is still genuinely open because the pipeline doesn't own settings.json.

**Lesson:** Verify that the *complete* deliverable exists, not just adjacent artifacts. Partial automation can leave work incomplete.

## Source Context

Emerged during KnowledgeForge 7.0 Phase 1 validation session (2026-05-22). The strategist mode was processing a backlog of issues in knowledgeforge-cc. Routine file inspection revealed two issues (kf-f1j, kf-8z4) whose deliverables had been completed by the kf-compile pipeline running against knowledgeforge-core sources. The pattern generalizes to any multi-repo compile setup where tracked work is silently completed by the build system.

This diagnostic pattern prevents the class of failures where work is genuinely done but the tracker doesn't know, leading to inflated work estimates and false "open backlog" signals in planning.
