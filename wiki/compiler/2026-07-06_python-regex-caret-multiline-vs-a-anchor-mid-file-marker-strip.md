# Python regex: `^` + `re.MULTILINE` vs `\A` — strip regexes must re-anchor when the marker's placement moves from top-of-file to mid-file

## What Was Learned

A cleanup regex written to strip a line-1 marker:

```python
pattern = re.compile(r'^<!-- Generated by kf-compile [^>]*-->\n', re.MULTILINE)
```

This looks like "match at start of file" — the `^` anchor plus a substring that historically only appeared at the top of the file. Under `re.MULTILINE`, however, `^` matches the start of ANY line, not just position 0. If the same marker later moves to a valid mid-file position (e.g., line 6 after a frontmatter block), the strip catches it there too and deletes it silently.

If the intent is specifically "only strip when the marker is on line 1," anchor to `\A` (string-start), which is not affected by MULTILINE:

```python
pattern = re.compile(r'\A<!-- Generated by kf-compile [^>]*-->\n')
```

No MULTILINE flag needed; `\A` matches only position 0.

## Concrete Grounding — knowledgeforge-core-oxp (2026-07-06)

`~/Scripts/knowledgeforge-cc/install.sh` had a defensive strip step for legacy kf-compile headers that used to appear on line 1 of agent files (7.17.1 era). The regex:

```python
pattern = re.compile(r'^<!-- Generated by kf-compile [^>]*-->\n', re.MULTILINE)
new_text = pattern.sub('', text, count=1)
```

When kf-compile 7.22.1 introduced "Option D" — placing the trace comment AFTER the frontmatter block (line 6+) instead of before it — the install strip caught the trace on line 6 and deleted it silently. Symptom: after `./install.sh`, the trace comment expected in the installed file was missing, even though the source file had it.

Fix:

```python
pattern = re.compile(r'\A<!-- Generated by kf-compile [^>]*-->\n')
```

`\A` guarantees start-of-string, so only a legacy line-1 comment is stripped; the new Option D placement (line 6) is preserved.

## The General Pattern

Any strip regex written for a marker that historically lived at the top of a file becomes fragile when the marker's canonical placement moves. Common cases:

- Codegen headers moved to accommodate a loader constraint (this session)
- Copyright banners re-positioned during a refactor
- Language-server directives shifted to fit a linter's expectations
- Compile stamps repositioned to keep line 1 machine-parseable

Rule of thumb:

- `^` + `re.MULTILINE` is only correct when you actually want to match at line-start ANYWHERE in the file.
- If you want strictly file-start, use `\A`.
- If you want strictly file-end, use `\Z`.

## Verification

```python
import re
line1  = re.compile(r'^X\n', re.MULTILINE)
strict = re.compile(r'\AX\n')

text = "A\nX\nB\n"  # X on line 2
line1.sub('',  text, count=1)   # 'A\nB\n'   — line 2 stripped
strict.sub('', text, count=1)   # 'A\nX\nB\n' — untouched (X not at position 0)
```

## When This Applies

- Install scripts that clean legacy markers
- Migration scripts that expect a marker in a specific position
- Codegen dedup logic
- Any regex written on the assumption "this pattern only ever appears at the top"

## When This Does NOT Apply

- Regexes that intentionally want to match at every line start (log line prefixes, comment stripping across a file)
- Substring searches without anchors (no positional constraint)
